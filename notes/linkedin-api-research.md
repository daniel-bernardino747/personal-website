# API Research: Writing to LinkedIn Programmatically (2026)

> Researched: 2026-07-22
> Method: WebFetch/WebSearch against first-party sources only (learn.microsoft.com/linkedin/*, developer.linkedin.com, linkedin.com/help, linkedin.com/legal)
> Subject: Can a third-party app write to a LinkedIn member's profile and feed? Framing question — can a git repo be the source of truth that syncs out to LinkedIn, GitHub, and a static site?

---

## Bottom line

- **Profile writes are not achievable.** LinkedIn does document a full Profile Edit API (positions, educations, skills, certifications, headline, summary, vanity name), but it is gated behind exactly one permission — `w_compliance` — and LinkedIn's own access page lists Compliance as **"Closed"** with the note "Access is closed and may not be requested." There is no partner tier you can apply to. ([Profile Edit API](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-edit-api), [Getting Access](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access))
- **Posting to your own feed IS achievable, self-serve, today.** Add the "Share on LinkedIn" product in the Developer Portal → get `w_member_social` → `POST /v2/ugcPosts`. No partner review, no business entity required. Capped at **150 requests/member/day**. ([Share on LinkedIn](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/share-on-linkedin))
- **Reading your own profile self-serve gets you almost nothing** — the OIDC `userinfo` endpoint returns name, picture, locale, email. No positions, no education, no skills, not even the headline. ([Sign In with LinkedIn using OIDC](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2))
- **There is exactly one self-serve way to read your full work history — and it's EU-gated.** The DMA-driven Member Data Portability (Member) API returns `POSITIONS`, `EDUCATION`, `SKILLS`, `CERTIFICATIONS` and ~65 other domains, but access tokens can only be generated by "members located in the European Economic Area and Switzerland." It is **read-only**. ([Member Data Portability (Member)](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/member-data-portability-member/?view=li-dma-data-portability-2026-05), [Snapshot Domains](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/shared/snapshot-domain?view=li-dma-data-portability-2026-05))
- **The "Add to Profile" escape hatch has been closed too.** It used to accept pre-filled certification parameters; LinkedIn removed autofill — it is now a static URL and "members must enter the relevant information directly on their profile." ([LinkedIn Help a528030](https://www.linkedin.com/help/linkedin/answer/a528030))
- **Net practical answer for the three sync targets:** website = full control (it's your repo); GitHub = programmatic profile write works via `PATCH /user`; LinkedIn = **posts yes, profile no**. For the profile, the only honest pattern is *generate and review manually* — render the repo data to a paste-ready block or a PDF/JSON resume and update LinkedIn by hand.

## 1. Profile writes — positions, education, certifications, skills, headline, summary

### The API exists and is fully documented

[Profile Edit API](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-edit-api) documents `POST https://api.linkedin.com/v2/people/(id:{person ID})` with rest.li `$set`/`$delete` patch semantics. Supported basic fields include `headline`, `summary`, `vanityName`, `industryId`, `geoLocation`, `profilePicture`, `backgroundPicture`, `websites`, plus ordering arrays (`positionsOrder`, `educationsOrder`, `skillsOrder`, `certificationsOrder`).

Complex sections get their own sub-resources with full CREATE / PARTIAL_UPDATE / DELETE support: [positions](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-edit-api/positions), [educations](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-edit-api/educations), [skills](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-edit-api/skills), [certifications](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-edit-api/certifications), courses, honors, languages, organizations, patents, projects, publications, test scores, volunteering experiences.

So on paper this is *exactly* the API a "repo as source of truth" sync would want.

### But the only permission that unlocks it is closed

The Profile Edit API permissions table lists **one** permission:

> | w_compliance | Required to manage and delete data for compliance. This is a private permission and access is granted to select developers. |

And the page header states:

> "The use of this API is restricted to those developers approved by LinkedIn and subject to applicable data restrictions in their agreements."

Cross-referencing [Getting Access to LinkedIn APIs](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access) (page `ms.date` 2025-06-24, docs `updated_at` 2026-06-03 — the most current access-control page I found), `w_compliance` appears under a section headed **"Compliance (Closed)"**:

> "The following permissions used for Compliance integrations are listed for reference purposes only. **Access is closed and may not be requested.**"

**This is the decisive finding.** Unlike Marketing (apply via portal), Sales/SNAP (apply to become a partner), or Talent (apply via ATS partner application), Compliance has no application path at all. As of 2026-07-22 there is no partner program, no tier, and no form that grants profile write access.

Two corroborating structural signals that this is a compliance-archive API rather than a career-management API: the Profile Edit API page carries `ROBOTS: NOINDEX` in its metadata, and its table-of-contents pointer (`toc_rel`) resolves to the **compliance** TOC, not the consumer or marketing one. The API's stated purpose — "manage and delete data for compliance" — is about regulated industries (finance, government) archiving and redacting employee LinkedIn activity, not about profile syncing.

The docs also impose usage requirements that rule out an automated one-way sync even if you had access:

> - The user must request the change to their profile
> - The users change must be posted unaltered to the profile

### Was there ever an open version? The v1 history

Yes, partially — and no, not for writes. LinkedIn's v1 API offered `r_basicprofile` and (referenced but not first-party-documented anywhere I could reach) `r_fullprofile`. Per the [Self-Serve Migration FAQ](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/migration-faq):

> "All new applications created on the LinkedIn Developer Platform as of January 14, 2019 can use LinkedIn's v2 APIs. **Starting May 1, 2019, LinkedIn will deprecate use of its v1 APIs.**"

The FAQ's own permission mapping shows the v1 surface was read + share only, never profile write:

| v1 permission | v2 replacement |
|---|---|
| `r_basicprofile` | `r_liteprofile` |
| `r_emailaddress` | `r_emailaddress` |
| `w_share` | `w_member_social` |
| `rw_company_admin` | (Marketing API Program) |

Note `w_share` → `w_member_social`: the only member *write* v1 ever exposed self-serve was posting, which survives to this day. Profile editing was never in the open tier.

The FAQ also documents the read narrowing explicitly:

> "In the interest of providing members with greater control over their data, Sign In with LinkedIn using OpenID Connect returns only the critical pieces of member data necessary for identification."

### Documentation ambiguity worth flagging

LinkedIn publishes complete, copy-pasteable request/response examples for an API that essentially nobody can obtain access to. The Profile Edit API pages have not been substantively updated in years (`ms.date` 2021-05-05 for positions, 2022-06-01 for the index) while the access page that closes the door was refreshed in 2026. Anyone reading only the Profile Edit API pages would reasonably conclude this is buildable. **It is not.** Treat search results and blog posts that cite these pages as a path forward with skepticism — they are citing real docs for an unreachable API.

## 2. Publishing posts to a member's feed

This is the one thing that genuinely works self-serve.

### The self-serve path (recommended for this use case)

Per [Share on LinkedIn](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/share-on-linkedin):

- **Product:** "Share on LinkedIn", added yourself in the Developer Portal → My Apps → Products tab.
- **Permission:** `w_member_social` — "Required to create a LinkedIn post on behalf of the authenticated member."
- **Access:** self-serve. [Getting Access](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access) lists it under **"Open Permissions (Consumer)"** — "available to all developers, and may be added via self-service." No partner review, no business entity, no screencast.
- **Endpoint:** `POST https://api.linkedin.com/v2/ugcPosts` with header `X-Restli-Protocol-Version: 2.0.0`.
- **Payload:** `author` (Person URN), `lifecycleState: "PUBLISHED"`, `specificContent.com.linkedin.ugc.ShareContent` with `shareCommentary` + `shareMediaCategory` (`NONE` / `ARTICLE` / `IMAGE`), and `visibility` (`PUBLIC` or `CONNECTIONS`).
- **Success:** `201 Created`, post ID in the `X-RestLi-Id` response header.
- **Rate limits (published on that page):** Member **150 requests/day**, Application **100,000 requests/day**, resetting at midnight UTC.

Images/video require a two-step register-then-upload against `POST /v2/assets?action=registerUpload` before referencing the returned `digitalmediaAsset` URN in the share.

### The versioned path (Posts API) and what "deprecated" actually means here

The [Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-04) is the modern replacement:

> "The Posts API replaces the ugcPosts API."

- **Endpoint:** `POST https://api.linkedin.com/rest/posts`
- **Required headers:** `Linkedin-Version: {YYYYMM}` **and** `X-Restli-Protocol-Version: 2.0.0`
- **Permissions table includes `w_member_social`** ("Post, comment, and like posts on behalf of an authenticated member").
- Supports update (`X-RestLi-Method: PARTIAL_UPDATE`, only `commentary`, `contentCallToActionLabel`, `contentLandingPage`, `lifecycleState`, `adContext` are mutable) and `DELETE`.

The [UGC Post API page is now titled "(Legacy)"](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/ugc-post-api?view=li-lms-2026-06) and carries a deprecation warning — **but read the scope of that warning carefully.** The warning says "The Marketing Version 202507 (Marketing July 2025) has been sunset," and the page then adds:

> "The above deprecation is applicable for **partners with Marketing permissions only**."

**So: the sunset dates being announced are Marketing API *version* sunsets (a rolling ~12-month window on `Linkedin-Version` values), not a sunset of the unversioned `/v2/ugcPosts` endpoint that the self-serve Share on LinkedIn product documents.** As of 2026-07-22 the self-serve Share on LinkedIn page still documents `/v2/ugcPosts` as the endpoint to call, and I found **no first-party sunset date for the unversioned consumer share endpoint**. This is a genuine documentation inconsistency: the consumer doc (last updated 2023-12-14) points at an endpoint the marketing docs label legacy.

Practical read: build against `/v2/ugcPosts` because that's what the self-serve product documents, but isolate the call behind one function so swapping to `/rest/posts` is a one-file change. Whether `w_member_social` obtained via Share on LinkedIn is accepted at `/rest/posts` is **not stated either way in the docs** — it is listed as a valid permission for that API, but the API lives in the Community Management program space. Verify empirically before depending on it.

### The reviewed path (Community Management API) — probably not available to you

If you wanted the versioned API officially, the product is Community Management, and it is heavily vetted. Per [Community Management App Review](https://learn.microsoft.com/en-us/linkedin/marketing/community-management-app-review?view=li-lms-2026-06):

> "At this time, our Community Management APIs are only available to **registered legal organizations for commercial use cases only**."

Requirements include: verified **business** email ("Personal email addresses won't pass the vetting process"), organization legal name / registered address / website / privacy policy, LinkedIn Page super-admin verification of the app, and — for Standard tier — a narrated screencast demonstrating each use case. Two tiers: Development (limited volume) then Standard (production).

A personal career-data sync project run by an individual does not meet the "registered legal organization, commercial use case" bar. The relevant approved use cases are framed as "Executive Management" and "Employee Advocacy" — a brand posting through employees' profiles — not an individual managing their own.

**Documented timelines:** the access-request survey "must [be completed] within 21 days from the date it is triggered," and Development tier integration must be completed "within twelve months of receiving the API access." **No review turnaround SLA is published.** [LinkedIn Help a1449586](https://www.linkedin.com/help/linkedin/answer/a1449586) lists review *statuses* ("We are reviewing your access request form responses", "We are verifying whether your organization meets our access requirements", "We are reviewing your developer application and screencast") and 11 rejection reasons, but states no duration — it directs timeline questions to developer support.

Rate limits for Community Management Development tier, from the [overview FAQ](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/community-management-overview?view=li-lms-2026-06): **500 requests per app**, **100 per member** (both recently increased from 100/10).

### You cannot read your own posts back

From the same overview FAQ:

> "**How do I get access to the Member Post Management program?** `r_member_social` is a **closed** permission. We're not accepting access requests at this time due to resource constraints."

The Posts API confirms `r_member_social` is "**restricted** and is available to **approved users only**", and that it is required "to retrieve all posts authored by a person." So a sync tool can write posts but cannot list what it previously wrote. **Design implication: your repo must be the sole record of what has been posted** — keep a local ledger of post URNs returned in `X-RestLi-Id`, because you cannot re-derive it from the API.

## 3. Profile reads

### Sign In with LinkedIn using OpenID Connect (current, self-serve)

Per [Sign In with LinkedIn using OpenID Connect](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2):

**Scopes:** `openid` (get the ID token), `profile` ("member's lite profile including their id, name, and profile picture"), `email`.

**Endpoint:** `GET https://api.linkedin.com/v2/userinfo`

**Complete response schema — this is everything you get:**

| Field | Description |
|---|---|
| `sub` | Subject identifier |
| `name` | Full name |
| `given_name` | First name |
| `family_name` | Last name |
| `picture` | Profile picture URL |
| `locale` | Member's locale |
| `email` | Primary email — **optional**, may be absent |
| `email_verified` | Boolean — **optional**, may be absent |

The [discovery document](https://www.linkedin.com/oauth/.well-known/openid-configuration) confirms `scopes_supported` is exactly `["openid", "profile", "email"]` and `claims_supported` adds only the standard JWT claims (`iss`, `aud`, `iat`, `exp`).

**No headline. No positions. No education. No skills. No summary.** For a career-data sync tool this endpoint is useful only for identifying *which* member authorized you — i.e. to build the Person URN you need for posting.

### Legacy scopes and their current status

| Scope | Returns | Status (as of 2026-07-22) |
|---|---|---|
| `r_liteprofile` | id, firstName, lastName, profilePicture ([Sign In with LinkedIn](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin)) | **Deprecated as of August 1, 2023.** "This version of Sign In with LinkedIn has been deprecated as of August 1, 2023." The product can no longer be added to new apps. |
| `r_emailaddress` | email via `GET /v2/emailAddress?q=members` | Deprecated alongside the above; superseded by the OIDC `email` scope |
| `r_basicprofile` | name, photo, headline, vanityName | **Restricted.** [Profile API](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-api): "restricted to those developers approved by LinkedIn." Docs also note "the v2 `r_basicprofile` permission grants only a subset of fields provided in v1." Not in the Open Permissions table. |
| `r_fullprofile` | — | **Could not verify** — see Unverified section |

The [Profile API](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-api) (`GET /v2/me`) technically exposes richer fields, but: "By default, only the Lite Profile Fields are returned... To request more or less fields, **you must have additional permissions that are only granted to select partners.**" It also carries a hard storage restriction: "You may never store data returned from the Profile API for members other than the authenticated member."

### Is there ANY self-serve way to read your own full work history?

**Yes — exactly one, and it is region-gated.** See section 5 (Member Data Portability). Outside the EEA/Switzerland, the answer is no API; only the manual data-export archive.

## 4. Rate limits and app review

### Rate limits

Per [LinkedIn API Rate Limiting](https://learn.microsoft.com/en-us/linkedin/shared/api-guide/concepts/rate-limits) (`ms.date` 2025-06-18):

- Two throttle dimensions: **Application** (total calls your app makes per day) and **Member** (calls a single member's token can drive per day, per app).
- All limits are **24-hour windows resetting at midnight UTC**. Exceeded limits return **429**.
- Critically: **"Standard rate limits are not published in documentation."** You look them up per-endpoint in Developer Portal → your app → **Analytics** tab — and that page "will only show usage and rate limits for endpoints you have made at least 1 request to today (UTC)." To discover a limit you must first call the endpoint once.
- Developer admins get **email alerts at 75%** of quota, with a stated **1–2 hour delay**, and only on application-level breaches — "not on member-level or combined member+app-level breaches."

Published exceptions (the numbers that ARE in the docs):

| Endpoint / program | Member/day | Application/day | Source |
|---|---|---|---|
| Share on LinkedIn (`/v2/ugcPosts`) | 150 | 100,000 | [Share on LinkedIn](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/share-on-linkedin) |
| Community Management, Development tier | 100 | 500 | [CM Overview FAQ](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/community-management-overview?view=li-lms-2026-06) |

For a personal sync tool, 150 posts/day is not a real constraint.

### App review / product request process

Three distinct tiers of friction:

1. **Self-serve (no review):** Sign In with LinkedIn using OpenID Connect, Share on LinkedIn. Add the product on the Products tab and you have the scope. This is the only tier relevant to an individual.
2. **Business-verified request:** e.g. Member Data Portability (3rd Party). Requires a LinkedIn Company Page whose **super admin verifies the app association**, plus "business email address and organization's legal name, registered address, website, and privacy policy," with email verification — "Personal email addresses will not pass the business verification process." ([MDP 3rd Party](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/member-data-portability-3rd-party/?view=li-dma-data-portability-2026-05))
3. **Full vetting:** Community Management / Advertising. All of the above plus an approved commercial use case, two tiers, and a narrated screencast for Standard. Notably, **rejection is not recoverable on the same app**: "You won't be able to re-apply for Development tier access with your existing app" — you must create a new app.

**No first-party page states a review turnaround time.** The only hard deadlines documented run the other direction (developer must respond within 21 days; must complete integration within 12 months).

## 5. Official alternatives when direct write is blocked

### 5a. Member Data Portability (Member) API — read-only, EEA/Switzerland only

The DMA-driven product, and the only real API answer for reading full career data. Per [Member Data Portability (Member)](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/member-data-portability-member/?view=li-dma-data-portability-2026-05):

**What it gives you.** Two APIs: **Member Snapshot** (point-in-time full historical data) and **Member Changelog** (ongoing activity events, queryable only for the **past 28 days**).

Snapshot endpoint: `GET https://api.linkedin.com/rest/memberSnapshotData?q=criteria&domain={DOMAIN}`, with a hard version pin:

> "Append the header `Linkedin-Version: 202312` to all requests. **This endpoint only supports `202312`.** ... Requests using a version other than `202312` will fail with a `426 NONEXISTENT_VERSION` error."

The [snapshot domain list](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/shared/snapshot-domain?view=li-dma-data-portability-2026-05) runs ~68 domains. The career-relevant ones map almost perfectly onto a resume schema:

| Domain | Description (verbatim) |
|---|---|
| `PROFILE` | "The basic biographical information that makes up the member's LinkedIn profile." |
| `POSITIONS` | "Job roles listed on the member's profile, including company names, titles, descriptions, locations, and dates." |
| `EDUCATION` | "Schools listed on the member's profile, including dates attended, degrees earned, and activities participated in." |
| `SKILLS` | "Skills added to the member's profile." |
| `CERTIFICATIONS` | "Contains a list of certifications included in the member's profile." |
| `PROJECTS` | "Projects listed on the member's profile." |
| `PUBLICATIONS`, `PATENTS`, `HONORS`, `COURSES`, `LANGUAGES`, `ORGANIZATIONS`, `TEST_SCORES`, `VOLUNTEERING_EXPERIENCES` | all profile sections |
| `ENDORSEMENTS`, `RECOMMENDATIONS` | given and received |
| `MEMBER_SHARE_INFO` | "all shared or re-shared posts, including date, URL, shared comments, and visibility status" |

The sample `PROFILE` response confirms it returns `Headline`, `Summary`, `First Name`, `Last Name`, `Industry`, `Geo Location`, `Websites`, `Birth Date`, etc.

**Is it read-only?** Yes. Every documented operation is a `GET`. There are no create/update/delete endpoints, and the product is framed entirely around "end user data access and portability" obligations. **No write capability exists.**

**Access.** The product request itself is self-serve, with an unusual constraint: you must create the app against a specific LinkedIn-provided page —

> "Please do not create a new LinkedIn Company Page while creating the developer application. You will be able to request access to Member Data Portability (Member) API only if you use the default LinkedIn company page — Member Data Portability (Member) Default Company"

**The hard blocker.** Token generation is region-locked:

> "At this time, this feature is available only for LinkedIn members located in the **European Economic Area and Switzerland**, so only those members are able to consent and generate an access token."

The [LinkedIn Help page](https://www.linkedin.com/help/linkedin/answer/a6214075) states the same: "only members located in the EU/EEA or Switzerland...can utilize this functionality." Location is determined by the location on your LinkedIn profile. The 3rd-party variant is narrower still — EEA only, no Switzerland mentioned: "Only LinkedIn users from the European Economic Area are allowed to consent to share their LinkedIn data with 3rd party developer applications."

**Whether this path is open to you depends entirely on your LinkedIn profile location** — worth checking before designing around it. If you are EEA/CH-based, this is a legitimately good ingest path: repo ← LinkedIn one-time, then repo as source of truth going forward. It never becomes a *push* path.

### 5b. "Download your account data" archive — universal, manual

Available to everyone regardless of region, from Settings & Privacy → Data Privacy → "Get a copy of your data" ([LinkedIn Help](https://www.linkedin.com/help/linkedin/answer/a1339364)).

- Includes profile basics, **work history, education, endorsements**, messages, connections, job applications, learning activity.
- Timing: "If you select a specific type of data, we'll email you within minutes. If you select the larger download, you'll receive an email within 24 hours."
- **Limitations:** the download link expires — "The data will be available for download for 72 hours." Not available on mobile. It is a manual, human-in-the-loop export — there is no API to trigger it, so it cannot be automated. You only receive "the categories of data that are applicable to your account."

Good for a **one-time bootstrap** of the repo. Useless as a sync mechanism.

### 5c. "Add to Profile" — was the best workaround, now closed

LinkedIn offers an "Add to Profile" product in the [consumer product catalog](https://developer.linkedin.com/product-catalog/consumer), described as "Add certifications and degrees to members' profiles." Historically this accepted URL query parameters that pre-filled the certification form — the closest thing to a semi-automated profile write.

That capability has been removed. Per [LinkedIn Help a528030](https://www.linkedin.com/help/linkedin/answer/a528030):

> "Developers who implement Add to Profile can now use a **static URL** to generate their button. **Links will no longer be customized for a specific certificate or degree.** If a member wants to add certification or degree fields to their profile, they can continue to do so using the Add to Profile button. However, **it will no longer autofill and members must enter the relevant information directly on their profile.**"

Corroborating this: `addtoprofile.linkedin.com` — the former URL-builder microsite — now returns a **301 redirect straight to that help article**. The tooling is gone, not merely deprecated.

The help page's "last updated" is relative ("2 years ago") and does not date the change precisely; I could not find a dated first-party changelog entry for the autofill removal.

### 5d. What this leaves for LinkedIn profile sync

No first-party mechanism accepts structured profile data from a third party. The honest options:

1. **Generate a paste-ready artifact.** Render `positions`/`education`/`skills` from the repo into the exact text blocks LinkedIn's form fields expect, so updating is copy-paste rather than retyping. Low tech, actually works, no ToS risk.
2. **Generate a PDF/JSON resume** from the same repo data (JSON Resume schema is the obvious target) and attach/host it. This also feeds the website target for free.
3. **Post about changes** instead of syncing them — when a new position lands in the repo, auto-draft a "excited to share" post via `w_member_social`. This is the one write channel that is genuinely open.
4. **Do not** use unofficial scraping/automation libraries against LinkedIn. Beyond reliability, it is squarely against LinkedIn's terms and risks account restriction — and the account is the asset you're trying to maintain.

### 5e. The other two targets, for comparison

**GitHub — programmatic profile write works.** [`PATCH /user`](https://docs.github.com/en/rest/users/users?apiVersion=2022-11-28) updates `name`, `email`, `blog`, `twitter_username`, `company`, `location`, `hireable`, and `bio` for the authenticated user. Combined with normal repo commits (profile README, repo descriptions, topics), GitHub is fully scriptable from the repo. *(Single non-LinkedIn source, included only for the framing comparison.)*

**Your Next.js site — trivially achievable.** The data already lives in `src/data/` in this repo; a build step that reads canonical career JSON and emits `profile.ts` / `projects.ts` / `achievements.ts` makes the site a pure derived artifact. This should be the first target built, since it's the one with zero external gatekeeping.

**Suggested architecture given the constraints:** one canonical schema in the repo → generators fan out to (a) the Next.js site at build time, (b) GitHub via `PATCH /user` + README commit in CI, (c) a rendered PDF/JSON resume, (d) LinkedIn *posts* via `w_member_social`, and (e) a paste-ready LinkedIn profile diff that a human applies. Targets (a)–(d) automate cleanly; only (e) needs hands, and only when career facts actually change — which is rare.

- **`r_fullprofile`** — I found no first-party LinkedIn/Microsoft page documenting this scope, its field set, or its deprecation. - **A sunset date for the unversioned `/v2/ugcPosts` endpoint as used by self-serve consumer apps.** The published sunsets are Marketing *version* sunsets and are explicitly scoped to "partners with Marketing permissions only." No date found.
